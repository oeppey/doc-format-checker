## 一、独立功能：模板格式提取

用户先上传一份作为规范依据的 DOCX。后端用 `python-docx` 和 OOXML 读取纸张与边距、字体字号、段落格式、页码及可识别的结构格式，并展示**提取值、所在位置和属性来源**。



## 二、功能 1：格式检测

**输入**：待审 DOCX＋用户保存的标准模板版本。

后端将 DOCX 解析成统一文档数据，读取正文、节参数、表格位置、页眉页脚，以及 run 和样式继承得到的有效属性。先根据 Word 样式、大纲级别判断标题和正文等角色，再结合编号、字体和对齐等线索；判定冲突的段落标记待判定。

随后逐条运行模板规则：字体、字号、加粗、边距等可直接比较属性；标题序号、附件、署名日期等由对应的结构检查器处理；需要真实页面位置的规则交由页面定位流程处理。每条结果返回规则 ID、标准值、实际值、文档逻辑位置、严重程度和能否自动修复。

这一功能以 **Python＋DOCX/OOXML 解析和规则检查器**实现，常规检查不用模型。模板提取与待审文档检查是两个独立入口；审查只使用已经保存的模板，不临时从待审文档推断标准。

## 三、功能 2：错别字检测

**输入**：待审 DOCX 中适合检查的文字及其原文位置。

处理链路为：

1. 过滤文号、日期等无需检查的内容，记录跳过范围和原因。
2. 按句拆分，保留每句话在原段落中的字符偏移。
3. 用 ChineseErrorDetectorElectra 批量筛出嫌疑句。
4. 仅将嫌疑句送给 ChineseErrorCorrector4-4B 精检。
5. 校验模型给出的替换片段、原文位置和受保护的姓名、案号、术语，再产生错字 Finding。


## 四、功能 3：错误定位与标注

**输入**：格式和错字检测生成的 Findings。

每条 Finding 先有稳定的 **DOCX 逻辑位置**：节、正文或页脚、表格路径、段落、run、字符范围。因为前端要求逐页展示 Word，后端再将 DOCX 渲染成 PDF，用同一份 PDF 生成页图和提取页面文字坐标，把 Finding 映射到页号及矩形：

- **红色**：错别字，尽量定位到原文字词。
- **黄色**：格式错误，按 run、段落或页面区域标注。
- 跨行错误返回多个矩形；点击问题列表跳转到对应页。

页边距等页面级错误没有对应的“错误字”，应标注页面区域。无法可靠映射坐标的 Finding 仍进入列表，并明确标为“未精确定位”，不编造页面坐标。

渲染和坐标计算**不用模型**，但比属性检查耗费更多 CPU。本机 1–20 页样本的整份渲染约 19–22 秒；50–100 页还需实测。长文档应使用后台任务，并按需生成、缓存页图。LibreOffice 与 Microsoft Word 的分页差异要在目标字体环境中验收。

## 五、功能 4：一键修复并下载

前端**只提供一个“下载修复后的 Word”入口**，不让用户逐条勾选修复项。修复依据是**本次审查已经产生并在页面展示的错误清单**；页面标注用于展示，后端实际修改的是原始 DOCX，不修改 PDF。

点击后，后端使用审查时锁定的模板版本和原文件：

1. 按 Finding 的逻辑位置，修改全部具备安全修复方式的格式错误。
2. 对已定位、已通过校验的错字建议应用替换。
3. 保留原件，在原 DOCX 基础上另存新文件，避免丢失表格、图片、样式和页码域。
4. 重新解析并复查修复涉及的规则，生成修复明细，然后返回新 `.docx` 文件。
